# EXHIBIT walkthrough

Target length: 2 minutes 30 seconds. Record the final submission only after a real analysis and its share link have passed the release checks in TEST_REPORT.md.

## 0:00–0:20 — The problem

“A job application asks us to describe what we can build. A repository contains the implementation, but making a hiring manager find the relevant parts is a lot to ask. EXHIBIT connects a job requirement to code a reviewer can actually open.”

Show the landing page, then open the creation form.

## 0:20–0:55 — Two inputs

Paste a public repository you have reviewed and a short, realistic job description. Start the real analysis and show its actual stages. If the recording cuts waiting time, disclose the cut and report the measured duration.

“It resolves the current commit, extracts technical requirements, and inspects a bounded selection of source files. The repository is read as text; its code is never executed.”

## 0:55–1:40 — The decisive interaction

Open one real evidence card. Show its job quotation, highlighted source, and exact GitHub link. Follow that link to its immutable commit and line range.

“The model proposes an interpretation. The server separately checks that its file, line range, and quotation exist in the inspected source. That checks source correspondence; it does not prove who wrote the code or that the interpretation is correct.”

Show a partial or not-observed requirement if the genuine result contains one. Do not invent one for the recording.

## 1:40–2:10 — Context and sharing

Open the inspection manifest and point out the inspected-file count and scope limits. Copy the share link and open it in a fresh browser. Show the phone layout.

“The useful result is a small, inspectable evidence dossier. Missing evidence stays visible. The read-only link requires no account and expires after 30 days.”

## 2:10–2:30 — Scope judgment

“I focused on one complete interaction: repository and job description to inspectable evidence. I left out accounts, candidate scores, private repositories, and CV generation. The next validation is whether developers use a dossier in a real application and whether reviewers open the cited code.”

## Submission checklist

- Use a real analysis, not the synthetic browser fixtures.
- Review every displayed claim against its code before recording.
- Confirm the GitHub repository is publicly populated and the live model works.
- Confirm the shared result opens in a fresh browser and remains unexpired for review.
- Report observed latency and token use without turning them into a general performance guarantee.
- Do not submit the assessment or send Codebridge a message without the user's instruction.
